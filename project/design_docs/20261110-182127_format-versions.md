## Summary

SHCL has 2 version numbers. The program version is semver, as it is now. The format version is `MAJOR.MINOR` and names what the text means. Every file has a format stamp. A file without one gets its format worked out from its text and its mtime, and the next save writes the stamp. shcl reads, stamps, and converts every format a published version ever wrote.

## Background

- Releases before `v3.0.0-beta1` didn't write a stamp. Files from 1.x and 2.0 don't have one, and the `#` info block in 2.x doesn't have a Format row.

- beta1 writes `##    Format   3`, and so did dev builds before it whose syntax was different. gitsby's pin-era files read with every backslash doubled under beta1, and slodworld1's files from `a37aa2ce` load with errors. Both say `Format 3`. gitsby tells its own files apart by mtime.

- The answer in 3.0 was that pre-release files are on their own (2026100115403385), with a `from_v2` flag for a caller who knows better. Consumers kept hitting the gaps.

- If every file is stamped and every old format can be read, a later format can change without stranding the files already out there. That lets the format change fast.

## Decisions

JC made all of these calls on 2026-11-10.

- There are 2 versions. The program gets a major bump when the API breaks, per semver. The format gets `MAJOR.MINOR`.

- The current format is 3.0. It may stay 3.0 through API v4.

- A SHCL file always has a format stamp. When it doesn't have one, shcl works out the format and writes it.

- The format of an unstamped file comes from its mtime and a full scan of its content. When the content says a newer format than the mtime, the content wins. When the content can't tell, the mtime decides.

- The stamp names the newest format the file is compatible with taht this program can read.

- shcl reads, stamps, and converts every format a release or pre-release on GitHub wrote, plus the dev snapshots consumers are known to have pinned.

- A past format is named after the earliest program version that read it.

- A plain save writes `## SHCL format 3.0`. The info block still has its aligned row, `##    Format   3.0`. Both are read.

- A pre-release has no format of its own. Its files are read as its release's format, and the lines that read differently are reported.

- A dev snapshot that consumers pinned does get a format of its own, named with the shortest commit prefix that tells it apart, such as `3.0-a37`. shcl maps each name to the rules it reads by.

- A load works the format out in memory and never writes. Every save writes the stamp, and so do `upgrade_file` and `shcl upgrade`.

## Design

### Format numbers

- From 3.0 on, a MINOR bump adds syntax, and every file of an older minor of the same major reads the same. A MAJOR bump is for a change where some line can read differently (me).

- Past formats keep their program-version names, whatever changed in them. Which releases start a new format will be settled by a diff of each release's reading rules, which is the first child item.

	| Release      | Published  | Stamp it wrote       | Format
	|:---          |:---        |:---                  |:---
	| v1.0.0-beta1 | 2026-07-15 | none                 | 1.0
	| v1.0.0-beta2 | 2026-07-21 | none                 | 1.0
	| v1.0.0-rc1   | 2026-07-26 | none                 | 1.0
	| v1.0.0       | 2026-07-28 | none                 | 1.0
	| v1.1.0       | 2026-08-04 | none                 | 1.1, if the diff finds a change
	| v1.2.0       | 2026-08-04 | none                 | 1.2, if the diff finds a change
	| v2.0.0       | 2026-08-26 | none                 | 2.0
	| v3.0.0-beta1 | 2026-11-05 | `##    Format   3`   | 3.0

- Pinned dev snapshots fit between these, such as `3.0-a37` for `a37aa2ce`. Each consumer's lockfiles and vendored copies give the list.

### The stamp

- A save without the info block puts `## SHCL format 3.0` at the end of the file, or rewrites the stamp where it is.

- The info block stays opt-in. It comes from `init`, a creating `set --write`, or a caller who asks for it. Its row is `##    Format   3.0`.

- beta1's `##    Format   3` is still read. It names 3.0 unless the content says it's a pinned snapshot.

- Every line of the info block starts with `##`, which shcl uses for the lines it writes itself, such as `desc` lines and the Schema line. 2.x's block used `#`, which is one of the scan's tells.

- A stamp naming a newer format than the program reads is refused for saves, as `TooNew` is now.

### Finding the format of an unstamped file

- The content scan looks for tells, which are things only some formats accept or read one way. Examples are `◉` escapes, `[#N]` selectors, backslash escapes in quotes, comma lists, `*` items, and a `#` info block. From them it gets the oldest format the text can be, and the formats it rules out.

- The mtime gives the newest format published before it.

- The rule:
	- When the content's oldest possible format is newer than the mtime's, the content's wins.
	- Otherwise the mtime's wins, if the content allows it.
	- If the content rules the mtime's out, the newest format the content allows that's older than it wins.

- Text that doesn't come from a file doesn't have an mtime, as with text from `parse`. Then the content decides alone, and text it can't place is taken as current (me).

- A caller can name the format with `from`, or `--from=FORMAT` on the CLI. A named format overrides the stamp and the scan. It replaces `from_v2` and `--from-2x`.

### Reading and converting

- "The newest compatible format" is the newest one under which the file reads the same as under the format it was found to be. A file that matches the current format is only stamped, and no line changes.

- Any other file is converted to the current format. A load converts in memory, so the document still has its path, and its save goes through every guard (2026111016205704). The save first copies the original under the backup name.

- Conversion goes one step per format, in order, as the Upgrade section of the v4 doc describes. Each step rewrites the lines it's sure of. A line it isn't sure of stays as typed and is reported by line number (2026111016205703).

- The steps are table-driven, so a new format adds a row and a step rather than new code paths in 4 bindings (me).

- Conversion goes into all 4 bindings and the 4 CLIs, by parity over idiom.

### What this replaces

- 2026100115403385, which left pre-release files on their own.

- The 2026101407100010 rules for `from_v2` on a stamped file. `from` takes their place.

- The rule that a library save never stamps. The info block rule stays as it is, so only `init` and a creating `set --write` add the block.

- In the v4 doc, "A file with no Format line is taken as this format", and the Format major read as a plain number.

- 2026111016205706, folded into this.

## Risks

- A copy, a git checkout, a restore, or a sync can make the mtime newer than the file. An old file without any tells then reads as current, as it does today. A caller who knows the format can name it with `from`.

- When 2 programs on different shcl versions share a file, the newer one stamps it. The older one then refuses to save it, as with `TooNew` now. That's the point of the stamp, but it's a new failure for programs that never saw one.

- Every format adds a step in 4 bindings, which is the cost of letting the format change.

## Testing

- The CLI built at each tag and each pinned commit is the oracle. Each reads the corpus and the fuzz output, and the converted reading has to match. check-migrate already does this for 2.0 (2026110409565662).

- The mtime cases are pinned with `touch -d`, on files whose content is ambiguous and on ones whose content says newer.

- The fuzz gets a property for the stamp on every save. A saved file has to name the current format, and a reload has to read it the same.

## Needs more thought

- It's still open which dev snapshots were pinned, and by whom. The list comes from each consumer's history.

- It's still open how short a commit prefix can be and stay unique among the formats. The table only has to tell its own rows apart.

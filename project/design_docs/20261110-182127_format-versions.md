## Summary

SHCL has 2 version numbers. The program version is semver, as it is now. The format version is `MAJOR.MINOR` and names what the text means. Every file has a format stamp. A file without one gets its format worked out from its text and its mtime, and the next save writes the stamp. shcl reads, stamps, and converts every format a published version ever wrote.

## Background

- Releases before `v3.0.0-beta1` didn't write a stamp. Files from 1.x and 2.0 don't have one, and the `#` info block in 2.x doesn't have a Format row.

- beta1 writes `##    Format   3`, and so did dev builds before it whose syntax was different. gitsby's pin-era files read with every backslash doubled under beta1, and slodworld1's files from `a37aa2ce` load with errors. Both say `Format 3`. gitsby tells its own files apart by mtime.

- The answer in 3.0 was that pre-release files are on their own (2026100115403385), with a `from_v2` flag for a caller who knows better. Consumers kept hitting the gaps.

- If every file is stamped and every old format can be read, a later format can change without stranding the files already out there. That lets the format change fast.

## Decisions

JC made all of these calls on 2026-11-10.

- There are 2 versions. The program gets a major bump when the API breaks, per semver. The format gets `MAJOR.MINOR`.

- The current format is 3.0. It may stay 3.0 through API v4.

- A SHCL file always has a format stamp. When it doesn't have one, shcl works out the format and writes it.

- The format of an unstamped file comes from its mtime and a full scan of its content. When the content says a newer format than the mtime, the content wins. When the content can't tell, the mtime decides.
	- JC replaced this order on 2026-11-17 (2026111707384944). The stamp comes first, then the mtime, then the tells, then the most legal reading. Content that looks newer than the mtime no longer beats it. The steps are under [Finding a file's format](#finding-a-files-format).

- The stamp names the newest format the file is compatible with taht this program can read.

- shcl reads, stamps, and converts every format a release or pre-release on GitHub wrote, plus the dev snapshots consumers are known to have pinned.

- A past format is named after the earliest program version that read it.

- A plain save writes `## SHCL format 3.0`. The info block still has its aligned row, `##    Format   3.0`. Both are read.

- A pre-release has no format of its own. Its files are read as its release's format, and the lines that read differently are reported.

- A dev snapshot that consumers pinned does get a format of its own, named with the shortest commit prefix that tells it apart, such as `3.0-a37`. shcl maps each name to the rules it reads by.

- A load works the format out in memory and never writes. Every save writes the stamp, and so do `upgrade_file` and `shcl upgrade`.

## Design

### Format numbers

- From 3.0 on, a MINOR bump adds syntax, and every file of an older minor of the same major reads the same. A MAJOR bump is for a change where some line can read differently (me).

- Past formats keep their program-version names, whatever changed in them. A release starts a format when its CLI reads some document differently from the release before it. The documents were every corpus file of every tag and a fuzz dump, 1,587 in all (2026111018212701).

	| Release      | Published  | Stamp it wrote       | Format
	|:---          |:---        |:---                  |:---
	| v1.0.0-beta1 | 2026-07-15 | none                 | 1.0
	| v1.0.0-beta2 | 2026-07-21 | none                 | 1.0
	| v1.0.0-rc1   | 2026-07-26 | none                 | 1.0
	| v1.0.0       | 2026-07-28 | none                 | 1.0
	| v1.1.0       | 2026-08-04 | none                 | 1.1
	| v1.2.0       | 2026-08-04 | none                 | 1.1
	| v2.0.0       | 2026-08-26 | none                 | 2.0
	| v3.0.0-beta1 | 2026-11-05 | `##    Format   3`   | 3.0

- rc1 reads every document the way v1.0.0 does. beta1 and beta2 each read some documents differently from the one after, and fold into 1.0 as pre-releases. rc1 added the 512-level depth cap.

- 1.1 is a format of its own. v1.1.0 folds a block, or a stacked list that closes onto an earlier instance's value, into the matching earlier instance. 1.0 kept 2 instances there, and its own `fmt` output then read back as 1. No text tells 1.0 from 1.1, so the mtime does.

- v1.2.0 reads every document the way v1.1.0 does, so there isn't a format 1.2.

### Pinned dev snapshots

- Consumers pinned 15 dev commits between v2.0.0 and v3.0.0-beta1, in Cargo and Go lockfiles, a Cargo `[patch]`, vendor pin lists, and the source lines of vendored `shcl.h` copies. Commits that read every document the same share one format, named after the earliest of them, as a release is (me).

- The name is the commit's first 3 characters (me). 2 already tell the 15 apart, but `3.0-b1` would read as beta1, and 3 matches the `3.0-a37` the decisions use. Each pin's own name is accepted as another name for its format, so a consumer can name the commit it pinned (me).

	| Format  | Commit     | Date       | Pinned by
	|:---     |:---        |:---        |:---
	| 3.0-1f8 | `1f880093` | 2026-09-24 | gitsby
	|         | `8711b460` | 2026-09-24 | silkterm
	| 3.0-30d | `30d36727` | 2026-09-25 | silkterm
	|         | `0c9b75b1` | 2026-09-25 | gitsby
	|         | `00fbb3e2` | 2026-09-25 | nemo-anywhere
	|         | `f2a8ad2a` | 2026-09-25 | gitsby, silkterm, nemo-anywhere
	| 3.0-b10 | `b10c2009` | 2026-10-01 | gitsby, silkterm
	| 3.0-f8e | `f8e27a22` | 2026-10-03 | convert-base-v2
	| 3.0-a37 | `a37aa2ce` | 2026-10-04 | slodworld1
	|         | `2317df56` | 2026-10-05 | convert-base-v2
	| 3.0-9ef | `9effd271` | 2026-10-14 | lxqtukz
	|         | `ea0998fa` | 2026-10-15 | shclwrap
	| 3.0-a65 | `a65eceb8` | 2026-10-25 | shclwrap
	|         | `2174f0d9` | 2026-10-26 | shclwrap, gitniblet
	|         | `a010fdf8` | 2026-10-28 | shclwrap, gitniblet

- What each one reads differently from the format before it:
	- 3.0-1f8, from 2.0, among others: a backslash is plain text outside double quotes. A bracketed value such as `[1, 2]` is no longer one element, and the line binds nothing. `name:[disc]` loses its children, with `E019`. `init` writes the `##` info block with `##    Format   3`.
	- 3.0-30d: only where a line has an error, such as kept lines and indents under a refused line.
	- 3.0-b10: `\uXXXX` escapes in double quotes, and octal and binary ints.
	- 3.0-f8e and 3.0-a37: only where a line has an error.
	- 3.0-9ef: the format 3 value syntax. `◉` escapes, and a backslash is plain text everywhere. `[a, b]` arrays and `-` items, and comma lists and `*` items are errors. Selectors go in parens. A bare name starts with a letter. A backtick value is quoted. A quoted thousands number is text. 2 spellings of one name, such as `"a\"b"` and `'a"b'`, are 2 fields again, as in 1.x.
	- 3.0-a65: an apostrophe inside a bare word, such as `it's`, is text again, which 3.0-9ef refused. The rest is only where a line has an error.
	- 3.0, at v3.0.0-beta1: only where a line has an error.

- So on every document tried, a file that loads clean under each format of a run reads the same under all of them. The runs are 3.0-1f8 and 3.0-30d, 3.0-b10 to 3.0-a37, and 3.0-9ef to 3.0. Such a file's stamp names the newest of its run.

### The stamp

- A save without the info block puts `## SHCL format 3.0` at the end of the file, or rewrites the stamp where it is.

- The info block stays opt-in. It comes from `init`, a creating `set --write`, or a caller who asks for it. Its row is `##    Format   3.0`.

- beta1's `##    Format   3` is still read. It names only the major, so the mtime and the content pick which 3.0 format it is, as [Finding a file's format](#finding-a-files-format) says.

- Every line of the info block starts with `##`, which shcl uses for the lines it writes itself, such as `desc` lines and the Schema line. 2.x's block used `#`, which is one of the scan's tells.

- A stamp naming a newer format than the program reads is refused for saves, as `TooNew` is now.

### Finding a file's format

- A file's format is worked out in 4 steps, in the order JC set on 2026-11-17 (2026111707384944). They start from every format this program reads, and each step takes formats off that list.

- First, the stamp. A stamp that names a whole format, such as `3.0` or `3.0-a37`, settles it, and the other steps don't run. beta1's `##    Format   3` names only a major. 3.0-1f8 to 3.0 all wrote it, so it leaves those 8 formats on the list. A Format line whose number doesn't read, such as `3x`, isn't a stamp. Where lines name more than one format, the highest decides, as it does now.

- Next, the mtime. Every format published after the mtime comes off the list, since no program could have written the file in it yet. The mtime doesn't rule out an older format, because a program pinned to an old shcl still writes that format after newer ones are out. The newest format left is the mtime's pick.
	- A format counts from the day before its date in the tables above, so the writer's time zone doesn't matter. A release's date is the day it was published, and a pin's is its commit date (me).
	- A dev build that wrote a file before a release was published is read as the format before that release. No consumer pinned such a build, and between 3.0-a65 and 3.0 the 2 differ only where a line has an error.
	- An mtime before 2026-07-14 is ignored, since no format existed yet and it comes from a box whose clock wasn't set (me).
	- An mtime that would take every format off the list is ignored too, such as `Format 3` on a file dated before 2026-09-23. The stamp wins there, since only shcl writes one, at the save (me).
	- Text that doesn't come from a file doesn't have an mtime, as with text from `parse`, so this step is skipped.

- Next, the tells, from the table under [Tells](#tells). A footer leaves only the formats whose `init` wrote it. A spelling that a format refuses, or reads as binding nothing, takes that format off the list. A spelling that 2 formats read differently but both read clean, such as `'C:\temp'`, doesn't take anything off (me). When every format left reads the file the same, the newest of them is the answer.

- Last, the most legal reading. This step runs when the formats left still read the file differently, or when the tells took off every format the stamp and the mtime left. Each format the stamp and the mtime left gets a count of the lines with a tell that it refuses or reads as binding nothing. The lowest count wins, and a tie goes to the newest. So the mtime's pick stands unless an older format reads the file more cleanly (me).
	- Only lines with a tell are counted, since every other line reads the same in every format, a missing colon included.
	- A spelling that reads clean both ways isn't scored. Which one the writer meant can't be read off the text, so the tie goes to the mtime's side.
	- A file whose content needs a newer format than its mtime allows reads by the format the mtime allows that refuses the fewest of its lines. Those lines are kept as typed and reported, as any error is.
	- Text without an mtime goes the same way, and a tie goes to the current format (me).

- Rejected:
	- The 2026-11-10 order, where content that says a newer format beats the mtime. JC reversed it.
	- Scoring every format the stamp allows in the last step, without the mtime's limit. Content that reads cleaner under a newer format would beat the mtime again, which is the order JC reversed.
	- Taking the mtime's pick as exact, so the tells could only choose among formats published near it. A file written today by a program on v1.2.0 would then read as 3.0.
	- Scoring a spelling that reads clean both ways by which format gives it a meaning, such as an escape over plain text. `'C:\temp'` reads with a tab under 2.0, and a Windows path almost never means that.

- A caller can name the format with `from`, or `--from=FORMAT` on the CLI. A named format overrides the stamp and the scan. It replaces `from_v2` and `--from-2x`.

### Tells

- Each row is a spelling and how each format reads it, from the CLI built at each tag and pin. "1.0 to 2.0" takes in 1.1, and "3.0-9ef on" takes in 3.0-a65 and 3.0.

	| Text                                         | Read as
	|:---                                          |:---
	| A backslash in single quotes or a bare value, `'C:\temp'` | 1.0 to 2.0: an escape, so `\t` is a tab. 3.0-1f8 on: plain text.
	| A backslash in double quotes, `"x\ty"`       | 1.0 to 3.0-a37: an escape. 3.0-9ef on: plain text.
	| `\u00e9` in double quotes                    | 3.0-b10 to 3.0-a37: a code point. The rest: plain text.
	| `◉TAB◉`, quoted or bare                      | 3.0-9ef on: an escape. Before: plain text.
	| A comma list, `a: 1, 2`                      | 1.0 to 3.0-a37: 2 elements. 3.0-9ef on: an error, kept as typed.
	| A bracketed value, `a: [1, 2]`               | 1.0 to 2.0: one element, `1, 2`. 3.0-1f8 to 3.0-a37: binds nothing. 3.0-9ef on: 2 elements.
	| `*` items under a field                      | 1.0 to 3.0-a37: an array. 3.0-9ef on: errors.
	| `-` items under a field                      | 3.0-9ef on: an array. Before: errors, and the field is empty.
	| A bracket selector in a line, `s["p"].h: 1`  | 1.0 to 3.0-a37: a selector. 3.0-9ef on: `E029`, kept as typed.
	| A paren selector in a line, `s(p).h: 1`      | 3.0-9ef on: a selector. 1.0 and 1.1: dropped. 2.0 to 3.0-a37: `E014`, kept as typed.
	| `name:[disc]` with children                  | 1.0 to 2.0: a selector, with `E015`. 3.0-1f8 to 3.0-b10: `E019`, and the children are lost. 3.0-f8e on: an error, kept as typed with its children.
	| A bare name that starts with a digit, `1a: x` | 1.0 to 3.0-a37: a name. 3.0-9ef on: `E014`.
	| A value in backticks                         | 3.0-9ef on: quoted, without the backticks. Before: text, backticks and all.
	| A quoted thousands number, `"1,200"`, read as an int | 1.0 to 3.0-a37: 1200. 3.0-9ef on: text.
	| 2 spellings of one name, `"a\"b"` and `'a"b'` | 2.0 to 3.0-a37: one field. 1.0, 1.1 and 3.0-9ef on: 2 fields.
	| An octal or binary int, `0o17`               | 3.0-b10 on: an int. Before: text.
	| A carriage return inside a bare value        | 1.0 to 3.0-a37: content. 3.0-9ef on: `E025`.
	| An apostrophe inside a bare word, `it's ok`  | 3.0-9ef: an error. The rest: text.
	| The `init` footer                            | 1.0: none. 1.1 to 2.0: a `#` block whose Home line names the old repository, with no Format row. 3.0-1f8 on: a `##` block with `##    Format   3`, with a Syntax link to `v3.0.0` from 3.0-1f8 and to `v3.0.0-beta1` from 3.0-30d on.

- No text tells these apart, so the mtime decides between them: 1.0 and 1.1, 3.0-1f8 and 3.0-30d once the footer is gone, 3.0-b10 to 3.0-a37, and 3.0-a65 and 3.0. Every pair but the first differs only where a line has an error.

- A `[#N]` selector in a line is `E014` in every format, so it isn't a tell. It's one only in a lookup path, which the scan doesn't see.

### Reading and converting

- "The newest compatible format" is the newest one under which the file reads the same as under the format it was found to be. A file that matches the current format is only stamped, and no line changes.

- Any other file is converted to the current format. A load converts in memory, so the document still has its path, and its save goes through every guard (2026111016205704). The save first copies the original under the backup name.

- Conversion goes one step per format, in order, as the Upgrade section of the v4 doc describes. Each step rewrites the lines it's sure of. A line it isn't sure of stays as typed and is reported by line number (2026111016205703).

- The steps are table-driven, so a new format adds a row and a step rather than new code paths in 4 bindings (me).

- Conversion goes into all 4 bindings and the 4 CLIs, by parity over idiom.

### What this replaces

- 2026100115403385, which left pre-release files on their own.

- The 2026101407100010 rules for `from_v2` on a stamped file. `from` takes their place.

- The rule that a library save never stamps. The info block rule stays as it is, so only `init` and a creating `set --write` add the block.

- In the v4 doc, "A file with no Format line is taken as this format", and the Format major read as a plain number.

- 2026111016205706, folded into this.

## Risks

- A copy, a git checkout, a restore, or a sync can make the mtime newer than the file. An old file without any tells then reads as current, as it does today. A caller who knows the format can name it with `from`.

- A clock that was set back, or a `touch -d`, can make the mtime older than the file. A newer file then reads by an older format's rules, and its lines in the newer syntax are reported. A save backs up the original before it converts anything, and `from` names the right format.

- When 2 programs on different shcl versions share a file, the newer one stamps it. The older one then refuses to save it, as with `TooNew` now. That's the point of the stamp, but it's a new failure for programs that never saw one.

- Every format adds a step in 4 bindings, which is the cost of letting the format change.

## Testing

- The CLI built at each tag and each pinned commit is the oracle. Each reads the corpus and the fuzz output, and the converted reading has to match. check-migrate already does this for 2.0 (2026110409565662).
	- check-migrate's 2.x oracle is `7be348d0`, a dev commit from 2026-09-07, not the v2.0.0 tag. They read 519 of the 1,587 documents differently. No consumer pinned it, so it isn't a format, and the 2.0 oracle is the tag.

- The mtime cases are pinned with `touch -d`. They're on files whose content is ambiguous, on ones whose content needs a newer format than the mtime, on `Format 3` stamps, and on an mtime before 2026-07-14.

- The fuzz gets a property for the stamp on every save. A saved file has to name the current format, and a reload has to read it the same.

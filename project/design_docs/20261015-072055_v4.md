# Version 4

Status: draft. Nothing here is built. It looks back over 1.0 to 3.0, and says what a v4 of the libraries and the CLI would do differently. All of it waits for v4 (JC, 2026-10-15). 3.0 goes out as `v3.0.0-beta1` with no full release, and v4 work starts after that.

Scope: the library interface in all four bindings, including how a document is stored, edited, formatted, and saved. Also the CLI's edit options, and how the bindings are split into files and tested. The value syntax in [value-syntax.md](value-syntax.md) stays as it is, and files stay Format 3.

## Summary

- A document keeps every line of its source as typed. The instance tree that reads use is an index built from those lines. An edit changes the lines it touches and no others.

- A save writes the lines back, so it can't drop a line nobody edited. `lost_count`, `save_file_lossy`, and the line-keeping save with its fallback to canonical text all go. One `save` is left.

- Formatting is its own step, `canonicalize()`, and it's what the CLI's `fmt` runs. It moves no line. Names come out the way they were first typed, and dotted lines and reopened blocks stay where they are.

- Load options are one `Options` value, which `parse_with` and `load_with` take. That replaces 9 load calls with 4, and `validate` is its own step.

- Reads have the 2 tiers `design.md` describes, with the same names in every binding: `read_*` gives a `Lookup` with the status, and `get_*_or` takes a fallback. No call is named plain `get_*`. Rust and C++ add a generic `read::<T>` and `get_or::<T>`.

- A document is walked and edited with node handles, `doc.root()` and `doc.node(path)`. A handle stays good through edits for as long as its node exists, and every setter has a form that takes one. Handles replace 19 path-string calls, and a loop over every instance no longer costs time in the square of the count.

- A merge applies one document to another as edits, so the receiver keeps its lines. `overlay` and `underlay` give the same values, and keep the text of whichever document they're called on.

- Names change where they mean two things, or the wrong thing. `set_*_default` is `ensure_*`, `set_literal` is `set_source`, `Read<T>` is `Lookup<T>`, and "banner" is "info block" everywhere.

- A field name no longer gives a bare number its unit. The program passes the unit, and a unit written in the value still wins.

- A note a setter writes into a file loses its date and time zone, and a backup is numbered rather than dated, so nothing in the library reads the clock.

- Only the Rust CLI is built. Go, Python, and C each get a small driver for the cross-binding check.

- The Rust crate and the Go package can be split into several files. C stays one header, and Python one module. A `serde` feature waits for after v4.0.

- Loose stays as it is in 3.0 (JC, 2026-10-15).

- `upgrade` stays, for this format change and later ones, and `migrate` folds into it. It's kept simple: each format step converts what it's sure of, and leaves the rest as typed (JC, 2026-10-15).

## Specification

What v4 does. The reasons are under [Design](#design).

### Storage

- A `Document` has 2 parts.
	- The lines. Every line of the source as typed, each with its own line ending, its indent, and the spans the tokenizer found in it. A line the parser couldn't use is still one of the lines, with its diagnostic beside it.
	- The index. The instance tree, built from the lines by the rules in `spec.md`. Nodes are `(name, value, children)` and merge on `(name, value)`, as in 3.0. A node points at the lines that opened it. The lines are the source of truth; the index caches what it derives from them, such as a resolved name or an array's display text, and nothing reads those caches but the index itself.

- `to_text()` joins the lines. A document nobody edited gives back its input byte for byte, a byte order mark and mixed line endings included.

- An edit reads the whole document again and rebuilds the index. A parse is linear and a config is small, so a setter on a 1,000-line file costs microseconds. A merge, `canonicalize()`, and `upgrade` make all of their changes first, then read the document again once. Reading again only the blocks an edit touched is deferred, since a dotted or selector line binds into another block, `(name, value)` merges span the file, and whether a kept line binds depends on every line above it. It stays an optimization behind the same interface, for after a measurement says it's needed.

- A document holds its text and its index, so it takes about twice the memory 3.0's tree did. For a config that's nothing. `comparison.md`'s peak-memory numbers are run again for v4.

- A document from `Document::new()` has no lines. Each setter adds lines the way canonical output writes them.

- A merged document keeps the lines of the document the merge was called on. See [Merging](#merging).

- Diagnostics come from the lines, at load and again after each edit. `diagnostics()` and `error_count()` stay.

- `design.md`'s Load outcomes table still says what the index does with each line: whether it binds, and which indent level it keeps open. Dropped and value dropped stop meaning a line is lost, since the line stays in the text either way. Nothing counts lost lines.

### Edits

- An edit is a change to some lines. A setter, `remove`, `set_comment`, `clear_comments`, and `set_info_block` each work out which lines to write, replace, or take out, make that change, and rebuild the index.

- A setter builds its line through the emitter and the tokenizer, as in 3.0, and the rebuilt index has to read back the value it was given. If it doesn't, the edit is undone and the setter returns `NoReadBack`.

- An edit never silently changes what a line it didn't write means. Two lines it didn't write can change, and both are said out loud:
	- A kept line that would bind once the edit is in becomes a comment with a note, as in 3.0. A kept line is one the index doesn't bind.
	- The lines under a kept field line start binding once a setter writes that field, since the field is there now. That's what the author typed them for.

- A changed value is written into the line that has it. The line's indent, its name as typed, its comment, adn its quote kind where the new value can take it, all stay.

- A value given by more than one line is changed on every one of them. That covers a leaf written twice, an instance opened twice, and an instance a selector names by value somewhere else. So `site(a.com)` set to `b.com` rewrites `site: a.com` and also `site(a.com).tls.hsts: off`.

- A new field goes after the last line of its parent's last block. That's the last line the index gives to anything under the parent: a field line, a raw body line, or a closing fence. Comments after it aren't in the block, so a new top-level field goes before the file's trailing comments and info block.
	- It's indented like its siblings. With no siblings it's one step under its parent, in the step the file uses most, or a tab in a file with none.
	- It ends the way most of the file's lines end.
	- A new top-level field gets a blank line above it when most of the file's top-level blocks have one. A nested field gets none.
	- Under a parent that only dotted lines opened, such as `log.level: warn`, it's a dotted line too, `log.file: x`, after the last of them.
	- A new instance of a field goes after the last one.

- `remove` takes the lines that opened the node, everything written under them, and the comment run right above each of those lines. A raw block's body and fences go with the line that opened it, whatever their indent. A dotted or selector line elsewhere that names the node goes too, with its own comment run. It adds no line, and it leaves the blank lines around what it took.

- A comment run is the comment lines right above a field line, with no blank line between. The run belongs to that field line. `comments(path)` returns it, `set_comment` replaces it, and `clear_comments` takes it out. A comment at the end of a field line belongs to that line. Any other comment belongs to nothing, and no edit moves it.

- A setter or an `ensure_*` that turns a line into a comment writes a note after it. The note no longer has a date or a time zone.

	~~~text
	# port: abc  ## replaced by shcl when ensuring port: not an int
	# a: O'Brien  ## commented out by shcl when setting a: E025 a quote in a bare value
	~~~

	- `SHCL_TEST_CLOCK` goes, since nothing in the library reads the clock. The backup `upgrade_file` makes is numbered, under [Upgrade](#upgrade).

### Formatting

- `canonicalize()` rewrites the document's lines in canonical form. `to_canonical()` returns the same text and leaves the document alone. `shcl fmt` is `to_canonical()`, and `fmt --write` is `canonicalize()` then `save()`.

- It changes how each line is written. It never changes which lines there are, or their order.
	- Indents are tabs, one per level.
	- Quoting follows Canonical output in [value-syntax.md](value-syntax.md), as in 3.0.
	- Blanks around `:` and inside brackets are the canonical ones.
	- Each name is written the way the field's first line has it. `Max-Upload-MB : 50` comes out as `Max-Upload-MB: 50`, where 3.0 wrote `max-upload-mb: 50`.
	- Dotted lines stay dotted, and a reopened block stays where it was written.
	- A repeated line stays. `H001` and `H002` still say so.
	- Every line ends the way most of the file's lines do, and a tie is LF. A CRLF file stays CRLF, and a mixed file comes out one way.
	- A byte order mark comes off. Trailing blanks come off every line but a raw body line.
	- A blank line is a line, so a run of them stays. 3.0 collapsed a run to one.
	- A line the index can't read stays byte for byte, since canonical form has no spelling for it.
	- A raw body line gets its block's new indent in place of the old one, by the fence rule in `design.md` under Formatter, and nothing else about it changes.

- An example. This input is canonical in v4 already, so `canonicalize()` leaves it alone:

	~~~text
	# top
	site: a.com
		root: /a
	site: b.com
		root: /b
	workers: 4
	# about hsts
	site(a.com).tls.hsts: off
	log.level: warn
	log.file: x
	workers: 4
	~~~

	- 3.0's `fmt` moves `hsts` and its comment into the `a.com` block, turns the `log` lines into a block, and drops the second `workers`.
	- So 3.0's `set --set workers=8` can't keep the file's lines, and prints the whole file in that form with a note on stderr. In v4 it changes lines 6 and 11 to `workers: 8` and nothing else.

- One kind of line can't go through `canonicalize()`. That's a kept line whose indent is tabs only, where the new indents around it would make it bind. `design.md` under Load outcomes settles that it isn't written as a comment, so:
	- `canonicalize()` changes nothing and returns those line numbers.
	- `canonicalize_lossy()` drops them.
	- `fmt --write` exits 7 unless given `--lossy`, and `fmt --check` exits 7 too.

- A second `canonicalize()` changes nothing. `fmt --check` exits 6 when `canonicalize()` would change a line, as in 3.0.

- Nothing folds reopened blocks together the way 3.0's `fmt` did. There's no option for it.

### Merging

- A merge applies one document to another as edits, by the merge rules in `spec.md`. The document it's called on keeps its lines, comments, and layout, and the result saves like any edited document. The argument's role is in the verb, so neither call reads two ways.
	- `doc.overlay(higher)` lays `higher` over `doc`, so `higher`'s values win. It's 3.0's `merge`.
	- `doc.underlay(lower)` lays `lower` under `doc`, so `doc`'s values win, and `lower` adds only what `doc` doesn't have.
	- `a.overlay(b)` and `b.underlay(a)` read the same. Only the text differs: each keeps its receiver's.

- What a merge writes:
	- A leaf that wins is written into the receiver's line for it, the way a setter writes a value. Where the receiver has that leaf on more than one line, the first takes the value and the rest become comments with a note, as a setter does with a kept line, since the merge rules replace them all and a merge deletes nothing typed.
	- A field or an instance the receiver doesn't have goes where a setter would put it, with its comment run from the other document above it.
	- A raw block fills an empty binding of its name, as in 3.0.
	- The other document's kept lines come in after the line before them, as in 3.0's Kept lines under edits table.

- Files given with `--layer` go under FILE, so the CLI builds the document with `underlay`, from the highest layer down: `FILE.underlay(L2).underlay(L1)` for `--layer=L1 --layer=L2 FILE`. What `fmt --layer` and `set --layer` print is FILE's text with what the layers add. `--write` with `--layer` stays refused, since a save would write the layers into FILE.
	- That's a right fold, `L1 + (L2 + FILE)`. 3.0 folds left, `(L1 + L2) + FILE`, and the two differ where a bare header meets a leaf of its name across layers, the example `design.md` gives under Layered loading. That example becomes a corpus case, so the change is on record rather than found later.

### Load and save

- One `Options` value has every setting a load takes. Its defaults are what `parse` and `load` use.

	~~~rust
	pub struct Options {
		pub strictness: Strictness, // Standard
		pub max_nodes: usize,       // 0 = no cap
		pub max_elements: usize,    // 0 = no cap
		pub max_diagnostics: usize, // 0 = no cap
	}

	impl Document {
		pub fn parse(text: &str) -> Document;
		pub fn parse_with(text: &str, opts: &Options) -> Result<Document, LoadError>;
		pub fn load(path: &str) -> (Document, FileStatus);
		pub fn load_with(path: &str, opts: &Options) -> Result<(Document, FileStatus), LoadError>;
		pub fn to_text(&self) -> String;
		pub fn to_canonical(&self) -> String;
		pub fn canonicalize(&mut self) -> Vec<usize>; // lines it couldn't place; empty when done
		pub fn canonicalize_lossy(&mut self);
		pub fn save(&self, path: &str) -> Result<(), IoError>;
	}
	~~~

- `_with` means one thing, "takes `Options`". In 3.0 it meant "takes a strictness" on `parse_with` and `load_file_with`, and "takes a parsed schema" on `load_and_validate_with`.

- Validation is its own step, `validate(&doc, &schema)`, as it is in 3.0. `load_and_validate` and `load_and_validate_with` go, since each was a load plus that one call.

- Only `Strict` makes `parse_with` and `load_with` fail, as in 3.0. The error has the document in it.

- `save` writes `to_text()` through the temp file and rename that 3.0's save uses, by the rows of `design.md`'s Save outcomes table. It never refuses over lines, since it can't lose one.

- Each binding has the same calls:

| Rust                                | Go                       | Python                             | C
| :---                                | :---                     | :---                               | :---
| `Document::parse(text)`             | `Parse(text)`            | `Document.parse(text)`             | `shcl_parse(text, len)`
| `Document::parse_with(text, &opts)` | `ParseWith(text, opts)`  | `Document.parse_with(text, opts)`  | `shcl_parse_with(text, len, &opts)`
| `Document::load(path)`              | `Load(path)`             | `Document.load(path)`              | `shcl_load(path, &status)`
| `Document::load_with(path, &opts)`  | `LoadWith(path, opts)`   | `Document.load_with(path, opts)`   | `shcl_load_with(path, &opts, &status)`
| `doc.to_text()`                     | `d.ToText()`             | `doc.to_text()`                    | `shcl_to_text(d)`
| `doc.to_canonical()`                | `d.ToCanonical()`        | `doc.to_canonical()`               | `shcl_to_canonical(d)`
| `doc.canonicalize()`                | `d.Canonicalize() []int` | `doc.canonicalize() -> list[int]`  | `shcl_canonicalize(d, &lines, &count)`
| `doc.canonicalize_lossy()`          | `d.CanonicalizeLossy()`  | `doc.canonicalize_lossy()`         | `shcl_canonicalize_lossy(d)`
| `doc.save(path)`                    | `d.Save(path) error`     | `doc.save(path)`, raises `IoError` | `shcl_save(d, path, &err)`
| `Options`                           | `Options`                | `Options`, a dataclass             | `shcl_options`, from `SHCL_OPTIONS_DEFAULT`

### Reads

- Every typed read has 2 tiers, named the same way in every binding.
	- `read_int(path)` returns a `Lookup<i64>`: the value, the status, and the rest of what 3.0's `Read<T>` has.
	- `get_int_or(path, fallback)` returns the value, or the fallback when the status isn't `Good`.
	- No read is named plain `get_int`.

- The types are int, float, bool, string, datetime, raw, and raw info, each with an array form where 3.0 has one, plus duration and size. The list doesn't change.

- `Lookup<T>` is 3.0's `Read<T>`, renamed. Its `raw` field is `source`, since `raw` already names a raw block. `line` is the value's line, and it's never 0 for a node an edit made, since in v4 an edit writes a line. A `Lookup` is a value read and nothing else: a call that answers with a count or a node uses the language's own value-and-status form, under [Traversal](#traversal).

	~~~rust
	pub struct Lookup<T> {
		pub value: T,
		pub status: Status,
		pub source: Option<String>, // the value as typed on its line
		pub slots: Vec<Status>,
		pub line: usize,
		pub quoted: bool,
		pub backtick: bool,
	}
	~~~

- What took the place of the middle tier:

| Binding | 3.0                                             | v4
| :---    | :---                                            | :---
| Rust    | `get_int(path) -> Result<i64, Status>`          | `read_int(path).ok()`, which gives `Option<i64>`, or `.into_result()`
| Go      | `GetInt(path) (int64, Status)`                  | `r := d.ReadInt(path)`, then `r.Value` and `r.Status`
| Python  | `get_int(path)`, which raises without a default | `doc.read_int(path).unwrap()`, which raises `StatusError`
| C++     | `get<T>(path)`, which returns the full read     | `read<T>(path)`
| C       | Already `shcl_read_int` and `shcl_get_int_or`   | No change

- Rust and C++ also have a generic form, as `spec.md` under The core call already says Rust does. It covers int, float, bool, string, datetime, and their arrays. Raw, raw info, duration, and size stay named, since they take more than a type.

	~~~rust
	let port: i64 = doc.get_or("server.port", 8080);
	let hosts = doc.read::<Vec<String>>("server(*).host");
	~~~

- Go keeps typed methods only. A Go generic would have to be a free function, `shcl.GetOr[int64](d, path, 80)`, which is a second way to say `d.GetIntOr(path, 80)`.

- Duration and size reads take the program's unit, and size takes a base in place of a bool:

	~~~rust
	pub fn read_duration(&self, path: &str, unit: Option<DurationUnit>) -> Lookup<std::time::Duration>;
	pub fn read_size(&self, path: &str, unit: Option<SizeUnit>, base: SizeBase) -> Lookup<i64>;
	pub enum SizeBase { Binary, Decimal } // KB to TB as 1024 or 1000
	~~~

### Traversal

- A node handle names one node in the index. Reads, edits, and the questions 3.0 asked by path, are calls on a node.

	~~~rust
	pub struct NodeId(u64);

	impl Document {
		pub fn root(&self) -> Node<'_>;
		pub fn node_by_id(&self, id: NodeId) -> Option<Node<'_>>;        // None once it's gone
		pub fn node(&self, path: &str) -> Result<Node<'_>, Status>;      // one instance
		pub fn nodes(&self, path: &str) -> Result<Vec<Node<'_>>, Status>; // every match, wildcards included
		pub fn node_mut(&mut self, id: NodeId) -> Option<NodeMut<'_>>;   // the node, for an edit
	}

	impl<'d> Node<'d> {
		pub fn id(&self) -> NodeId;
		pub fn name(&self) -> &str;          // as matched, escapes resolved
		pub fn authored_name(&self) -> &str; // as first typed
		pub fn value(&self) -> &str;         // display text; "" for a wrapper
		pub fn kind(&self) -> ValueKind;
		pub fn line(&self) -> usize;         // the first line that opened it
		pub fn lines(&self) -> Vec<usize>;
		pub fn path(&self) -> String;        // reads this node and no other
		pub fn parent(&self) -> Option<Node<'d>>;
		pub fn children(&self) -> Vec<Node<'d>>; // every child instance, in file order
		pub fn child_names(&self) -> Vec<String>;
		pub fn comments(&self) -> Vec<String>;
		pub fn node(&self, path: &str) -> Result<Node<'d>, Status>; // relative to this one
		pub fn nodes(&self, path: &str) -> Result<Vec<Node<'d>>, Status>;
		pub fn read_int(&self, path: &str) -> Lookup<i64>;         // "" reads this node
		// ... every read and get_*_or, as on Document
	}

	impl<'d> NodeMut<'d> {
		pub fn id(&self) -> NodeId;
		pub fn set_int(&mut self, path: &str, v: i64) -> SetStatus; // relative to this node
		pub fn ensure_int(&mut self, path: &str, v: i64) -> SetStatus;
		pub fn remove(&mut self, path: &str) -> Result<usize, Status>;
		pub fn set_comment(&mut self, path: &str, lines: &[&str]) -> SetStatus;
		// ... every setter, ensure_*, and comment call, as on Document
	}
	~~~

- `node` answers with the node or why not: `NotFound`, `Multiple`, or `BadPath`. `nodes` answers with every node the path reaches, in file order, an empty list when none, and `BadPath` when the path doesn't parse. Each language says "the value, or why not" its own way, as it does for the typed reads' unwrap: Rust `Result<T, Status>`, Go `(T, Status)`, Python a `(T, Status)` tuple, with `None` or an empty list for the value, and C an out-parameter with the status returned. `remove` and `clear_comments` answer the same way, with the count. A `Lookup` is for a value read only.

- Every read on `Document` is the same read on `doc.root()`. A loop reads each instance from its own node, so it doesn't look the path up again from the top. Every setter on `Document` is the same setter on the root node, so a loop edits where it stands. The doc's own example, a port under each site:

	~~~rust
	let ids: Vec<NodeId> = doc.nodes("site(*)")?.iter().map(Node::id).collect();
	for id in ids {
		if let Some(mut site) = doc.node_mut(id) {
			site.ensure_int("port", 443);
		}
	}
	~~~

	~~~go
	sites, _ := d.Nodes("site(*)")
	for _, site := range sites {
		site.EnsureInt("port", 443)
	}
	~~~

	- Without a node form, that loop goes through `site.path()`, which is index-based (`site(3)`), and an index shifts under a `remove` in the same loop. That's the bug handles exist to end.

- The 19 calls nodes replace: `paths`, `instance_paths`, `fields`, `read_fields`, `read_child_fields`, `children`, `read_children`, `instances`, `read_instances`, `line`, `read_line`, `lines`, `read_lines`, `kind`, `read_kind`, `authored_name`, `read_authored_name`, `comments`, and `read_comments`. The `Field` struct goes with them.

- `count` and `read_count`, and `exists` and `read_exists`, stay on `Document`. They're the questions a program asks most, and the CLI's `count` uses them.

- Every node has a `NodeId`. It stays the same through edits for as long as the node exists, a change to the node's own value included, and isn't used again after the node is gone. `canonicalize()` changes no `NodeId`, since it moves no line.
	- A handle is the document plus a `NodeId`, so a handle made before an edit still names the same node after it.
	- A call on a handle whose node is gone answers the way a lookup of a missing path does: `NotFound` from a read, an empty string or list, and line 0. No new status is needed.
	- `node.id()` gives the `NodeId`, and `doc.node_by_id(id)` gives the node back, or nothing once it's gone.
	- In Rust a `Node` borrows the document, so it can't be kept across an edit, and the edits are on `NodeMut`, which borrows it mutably. A program keeps `NodeId`s across an edit, as the loop above does. That's the one place the bindings differ, and it's the borrow checker's rule. Go and Python have one `Node` with the reads and the edits on it.
	- When the index is read again, a node keeps its ID by its parent's ID, its name, its value, and its ordinal among siblings with all three the same. Only repeated raw blocks have such siblings, since any other repeat merges.
	- A setter that changes a node's value hands the ID on. When the new value is a sibling's, the two nodes become one: the node the setter was given keeps its ID, and the sibling's ID is gone. So the handle a program is editing with stays good through its own edit.

- In C a node is its `NodeId`, `typedef uint64_t shcl_node;`. `SHCL_ROOT` is 1 and `SHCL_NO_NODE` is 0, so a zeroed variable names nothing.
	- `shcl_node_exists(d, n)` is C's `node_by_id`.
	- `shcl_node_at(d, base, path, len, &node)` and `shcl_nodes_at(d, base, path, len, &nodes, &count)` return the status.
	- `shcl_node_name`, `shcl_node_authored_name`, `shcl_node_value`, `shcl_node_kind`, `shcl_node_line`, `shcl_node_lines`, `shcl_node_path`, `shcl_node_parent`, `shcl_node_child_count`, `shcl_node_child(d, n, i)`, and `shcl_node_comments`.
	- The root forms stay as they are, `shcl_read_int(d, path, len)` and `shcl_set_int(d, path, len, v)`, so the common call gains nothing to type. The node forms take a node first: `shcl_node_read_int(d, n, path, len)`, `shcl_node_get_int_or(d, n, path, len, fallback)`, `shcl_node_set_int(d, n, path, len, v)`, `shcl_node_remove(d, n, path, len, &count)`. That mirrors the `Document` and `Node` split the other three have.

- Go and Python use the same words as Rust: `d.Root()`, `d.Node(path)`, `d.NodeByID(id)`, `n.ID()`, `n.Children()`, `n.ReadInt("")`, `n.SetInt(path, v)`, and `doc.root()`, `doc.node(path)`, `doc.node_by_id(id)`, `n.id()`, `n.children()`, `n.read_int("")`, `n.set_int(path, v)`.

- The CLI's `paths`, `children`, and `instances` subcommands stay, and walk nodes.

### Setters

- The `set_*` setters stay as they are.

- The default forms are `ensure_*`: `ensure_int`, `ensure_float`, `ensure_bool`, `ensure_string`, `ensure_datetime`, `ensure_raw`, `ensure_source`, and the array forms `ensure_int_array` through `ensure_datetime_array`. What each does is `design.md`'s Default forms table, unchanged.

- `set_literal(path, text)` is `set_source(path, text)`, and `set_literal_default` is `ensure_source`. It takes the value as a file line spells it, which is what `Lookup.source` gives back, so the two share the word. `SetStatus::NotOneValue` stays.

- `remove(path)` and `clear_comments(path)` return the count and a status, in each language's value-and-status form under [Traversal](#traversal). `try_remove` and `try_clear_comments` go. The setters return a status already, so these 2 were the odd ones out.

- `set_banner(on)` is `set_info_block(on)`.

- Every setter, `ensure_*`, `remove`, `set_comment`, and `clear_comments` has a node form, under [Traversal](#traversal).

- `check_set_path` and `set_comment` stay. `merge` is `overlay`, beside the new `underlay`, as under [Merging](#merging).

### Names in the file

- Field names still match without regard to ASCII case, as `spec.md` says under Merging and instances.

- Canonical output writes a name the way the field's first line has it. A setter that makes a field writes the name the way its path has it. A setter that changes a field keeps the line's own spelling.

### Units

- A field name no longer gives a bare number a unit. `timeout-ms: 250` is a bare number, and reads with the unit the program passes, or as `BadType` with none.

- A unit written in the value still wins over the program's: `timeout: 5s` is 5 seconds, whatever the read passed.

- `H005` is retired.

- A schema's `min` and `max` read with their own unit, else the schema's `unit`.

- The CLI's `--unit` is how a shell script passes the unit, as in 3.0.

### Upgrade

- `upgrade` makes a file written for an older format over for this one. It stays for the next format change too.

	~~~rust
	pub fn upgrade(text: &str, from: Option<u32>) -> Upgrade;
	pub fn upgrade_file(path: &str, from: Option<u32>) -> Result<Upgrade, IoError>;

	pub struct Upgrade {
		pub text: String,
		pub from: u32,             // the format it was written for
		pub changed: Vec<usize>,   // lines a step rewrote
		pub unsure: Vec<usize>,    // lines a step couldn't convert, left as typed
		pub backup: String,        // where upgrade_file put the original
	}
	~~~

- A file's format is the major its Format line names. A file with no Format line is taken as this format.
	- `from` overrides both. It's the caller saying the file is old, so it's for a file known to be old, never for every start. A `from` newer than the Format line is taken as given, since the caller knows better than the line. A `from` naming this format or a newer one means there's nothing to do.
	- So `upgrade_file(path, None)` is safe on every start. It leaves a current file alone.

- A file from an older format goes through one step per format, in order: 2 to 3, then 3 to 4 once there is one.
	- A step rewrites the lines it's sure of, as edits, so comments adn layout come through.
	- A line a step isn't sure of stays as typed. It loads as an error, which says where it is, and the backup has the original.
	- The 2 to 3 step keeps 3.0's easy conversions: comma lists to brackets, `*` items to `- ` items, bracket selectors to parens, and backslash escapes to `◉` escapes.

- The Format line is rewritten to name this format where it is, or added at the end.

- `upgrade_file` copies the original first, under `NAME_backup_format-vN.EXT`, then saves the new text with `save`. When that name is taken it counts up, `NAME_backup2_format-vN.EXT`, `NAME_backup3_format-vN.EXT`, to the first free one, by an exclusive create. So a second run never stops on the first run's copy, every backup of one file matches `NAME_backup*`, and no name reads the clock. 3.0 put a timestamp in the name for the first two reasons and needed `SHCL_TEST_CLOCK` to pin it.

- `upgrade_file` fails only the way a read or a write fails, as an `IoError`. A missing file is its `NotFound` kind.

- The CLI is `shcl upgrade [--write] [--check] [--from=N] FILE`. `--check` exits 6 when there's something to upgrade, and a failed read or write exits 8.

- `H007`, a Format line naming an older format, names `upgrade`. `H006`, for a newer one, stays.

## Goals

- A save keeps every line nobody edited, because of how the document is stored, with no rules on top to make it so.

- One way to do each thing: one save, one pair of read tiers, and one meaning per name.

- Fewer public calls that do the same things.

- A program can walk and edit a document without building path strings, in time that grows with its size.

- Less code written 4 times that has nothing to do with reading the format.

- Every file that reads clean in 3.0 reads the same in v4. The one exception is a bare number in a field whose name ends in a unit. The 3.0 corpus checks it, under [Properties](#properties).

### Non-goals

- Changes to the value syntax. [value-syntax.md](value-syntax.md) stands.

- Changes to Loose (JC, 2026-10-15).

- A Format 4. v4 is a library major. Files stay Format 3, and `FORMAT_MAJOR` stays 3.

- New bindings, or a shared library build, for the reasons in `design.md` under Integration modes.

- Changes to the diagnostic codes, apart from `H005` going, or to the schema vocabulary.

- A whole-document decode in v4.0. The `serde` feature is under [Deferred](#deferred).

- Converting every 2.x edge case. The 2 to 3 step converts what it's sure of (JC, 2026-10-15).

## Design

### Source text first

- 3.0 builds the instance tree and throws the text away. Output is written from the tree, so anything the tree doesn't have has to be put back by a rule.
	- Comments are filed onto nodes, by the rules under Formatter in `design.md`, and moved again after each merge, new child, and fold.
	- A line the parser couldn't use has 5 outcomes, and lost lines are counted. The save refuses on the count, and `--lossy` overrides it.
	- The emitter models the level stack a reload will have, to decide whether a kept line can be written as it was.
	- The line-keeping save lines up 2 canonical texts and splices the source back in, and falls back to canonical when the 2 don't line up.

- Load outcomes, Kept lines under edits, Default forms, and the comment rules are the densest part of `design.md`. By title, about 160 backlog items are about kept or lost lines, and about 80 about comments.

- In v4 the text is what's stored, and the tree is derived from it. A line nobody edited is written back because it's never been anywhere else. That's what toml_edit does in Rust, and what kdl-rs and rust-analyzer's syntax trees do.

- SHCL is read a line at a time, and the tokenizer already returns each line's spans. So a list of lines with their spans is enough. A full syntax tree with a node per token, the rust-analyzer kind, would be more than this needs.

- What still needs a rule is where a new line goes, and which comments go with a remove. Both are short, under [Edits](#edits).

- The 3.0 check that an edited text reloads as the edited document stays, as the setter's read-back. It decides whether an edit is allowed. It no longer decides how much of the file survives.

### Comment runs

- 3.0 files a comment onto a node, so a comment can move when the node does. Most of the comment rules under Formatter in `design.md` exist to keep that move from changing what a reader sees.

- v4 leaves a comment where it was typed. Only 3 questions need an answer: what `comments(path)` returns, what `set_comment` replaces, and what `remove` takes. The comment run right above a field line answers all 3. It's the same rule Go uses for doc comments.

- A comment with a blank line under it belongs to no field. No edit touches it, and a remove of the field below it leaves it.

### Canonical form moves no line

- 3.0's `fmt` makes a file over from its tree. It folds reopened blocks together, turns dotted lines into blocks, and drops a repeated line. Canonical order then isn't source order, and that's what makes 3.0's line-keeping save fall back. The example under [Formatting](#formatting) falls back on a one-value change.

- In v4 `canonicalize()` changes how a line is written, and nothing else. Two files that mean the same thing can have different canonical forms. That doesn't matter, since what's compared is one binding's output against another's for the same input.

- A dotted line staying dotted follows the same reasoning as keeping the author's quote kind, which `fmt` has done since 3.0. Both are the author's choice, and neither changes a read.

- Reopening a block far from where it began is still allowed, and `H002` still says it happened.

- There's no option to fold blocks the way 3.0 did. gofmt, rustfmt, Black, and Prettier don't move content either, and taplo's option to reorder entries is off by default. Folding changes the file's structure, which is a refactor, not formatting. An option for it would also keep 3.0's comment-filing code alive in four bindings. `H002` says where a block was reopened, for a person who wants to fold it by hand.

### Options in one value

- 3.0 has 9 ways to load: `parse`, `parse_with`, `parse_limited`, `parse_keep_lines`, `load_file`, `load_file_with`, `load_file_keep_lines`, `load_and_validate`, and `load_and_validate_with`. Each new option doubled some of them, and four bindings each have every one.

- `parse_limited` takes 3 caps and a strictness as 4 positional arguments. A caller who wants only a node cap passes 2 zeros and the default strictness.

- An options value grows a field without a new call. `keep_lines` stops being an option at all.

### Two read tiers

- `design.md` says every binding has 2 read tiers, and names the fallback tier `_or` so a routine ported between bindings can't keep the call name and change tier. In 3.0 a plain `get_int` means 4 different things.
	- Rust: a `Result<i64, Status>`.
	- Go: an `(int64, Status)` pair.
	- Python: the value, raising without a default, or the default.
	- C++: `get<T>`, the full read.

- `spec.md`'s own tier table lists Rust's full tier as `get_int` and Python's as `read_int`.

- 2026100717500011 took the plain `get_*` out of C for this reason. v4 takes it out of the other three. Each language's own way to unwrap a value is a method on `Lookup`, so nothing is lost.

### Node handles

- 3.0 walks a document by path. A program asks `instance_paths()`, gets strings back, and reads each one with another call that parses the path and looks it up from the top. Building a path from user text needs `quote_segment`.

- That costs time in the square of the instance count. 2026100307163919 measured 80 s in Rust to read each of 20,000 instances by value, and 3.8 s by index. It's deferred, since typical configs have under 1,000 instances.

- A node handle reads from where it is. It also replaces 19 calls, most of them in pairs, with one call per question on a node.

- A path string is still how a program names a field it knows. Handles are for walking, and for editing on the way.

- A handle stays good through edits because a program that walks a document often edits it on the way, such as setting a port under each `site`. A handle that went stale after the first edit would fail that loop on its second pass. Failing on use, the way Java's iterators do, was weighed and turned down for that reason, and so was a new `Stale` status.

- The edits take a node for the same loop. With reads on a node and edits by path only, the loop has to build a path from `node.path()`, which is an index, and a `remove` in the loop shifts every index after it. 3.0's `instance_paths` has that bug, and handles that can't edit would keep it.

- A node that's gone answers like a missing path, since that's what it now is. A removed element in the browser DOM works the same way.

- A node's ID survives a re-read by its parent, name, value, and ordinal, since that's what the index merges on, plus the ordinal for the one case that doesn't merge, a repeated raw block. When a setter's new value is a sibling's, the edited node keeps its ID, since that's the handle the program has in hand. Keeping the earlier line's ID instead, the way spelling and `line()` go to the first line, would make a program's own edit stale its own handle.

- Rust gets the same thing through `NodeId`, since a borrowed `Node` can't outlive an edit there. Edits go on a `NodeMut` from `node_mut(id)`, one more type, rather than an `_at(id, ...)` twin of every setter, since a mutable handle is how Rust's own collections do it (`get_mut`, `entry`) and the twins would be 25 more names.

- `node` and `nodes` answer with a value and a status in each language's own form, rather than a `Lookup`. A `Lookup` has `source`, `slots`, `quoted`, and `backtick`, which mean nothing for a node, and a `Lookup<Option<Node>>` would say "not found" twice. The same goes for `remove` and `clear_comments`, which answer with a count.

### Ensure in place of default

- "Default" means 3 things in 3.0: the schema's `default` entry, the CLI's `--default` fallback on a read, and the `set_*_default` setters. The setters do the most, since they fill a missing field, an empty one, or one whose value doesn't read as the type.

- `ensure` says what the setter does: after it, the field reads as that type. It was one of the options on 2026-10-09, beside changing the forms. The forms changed and kept the old name.

### Source in a setter

- "Literal" usually means taken as is. Helm's `--set-literal` takes its text as a plain string. SHCL's `--set-literal` reads its text as value syntax, which is the opposite.

- `--set-source` says what it does: the text is the value as a file line spells it. `Lookup.source` already uses the word for the value as typed, so a read and a write of the same thing share one term. "Syntax" was weighed and turned down as a third word for it. `--set` keeps taking data, since that's the common case in a shell and it needs no quoting.

- Turning it around the Helm way, `--set` reading syntax and `--set-string` taking data, was turned down. Every `--set 'title=My App'` in a script would then need inner quotes.

### `Lookup` in place of `Read`

- In Rust a `Read<T>` sits beside `std::io::Read`, and a file that imports both has to rename one. `lib.rs` imports `std::io::Read` itself, inside `read_file`.

- `Read` is also a verb, and also every typed read is named `read_*`. `Lookup` is the word `spec.md` uses for a point read.

- The field `raw` had the value as typed, while `read_raw` reads a raw block. `source` doesn't collide, and `set_source` is its write side.

- In Rust `source` could borrow the line it came from, now that the document keeps its text. It stays an owned string in v4.0, since the value beside it is owned anyway and a borrow would put a lifetime on every `Lookup`. It's under [Deferred](#deferred).

### Info block

- 3.0 calls the generated comment block 3 things. The interface says banner: `set_banner`, `GEN_BANNER`, `no_banner`, `--no-banner`, and the ops `banner on` and `banner off`. The CLI help and `design.md` say info block, and the generation notes in `design.md` say footer.

- `design.md` has one meaning per term as a rule. Info block is the term the help already uses.

- The negative knob stays, `no_info_block` and `--no-info-block`, for the reason in `design.md`: saying nothing gets the useful behavior.

### Units from field names

- In 3.0 a bare number's unit has 3 sources: the value, the field name, and the program. For a schema's `min` and `max` there's a fourth, the schema's `unit`. Each pair needed a precedence rule, and the name and the value disagreeing needed `H005`.

- A name ending in a unit is a guess, which the README says SHCL doesn't make. It needed carve-outs: `min`, `m`, and `s` aren't endings, since `retries-min` is a minimum and an `s` is usually a plural. A camelCase ending was tried and dropped, since names fold to lower case, and `fmt` turned `ttlHours: 1.5` from 1.5 hours into 1.5 seconds.

- The `H005` check slowed every parse (2026092813365305).

- The program knows the unit it wants. It passes it, and a unit in the value still wins. That leaves 2 sources and one rule.

### Name case in output

- Matching without regard to case is a convenience for the person typing. Lowercasing the output takes away what they typed.

- The README's example uses `Max-Upload-MB : 50` to show that messy spacing is fine. 3.0's `fmt` writes it as `max-upload-mb: 50`.

- `authored_name` already keeps the first spelling, so the output has it to hand.

### Notes without a clock

- A note with a date and a time zone ties a save's bytes to the clock. All four bindings needed `SHCL_TEST_CLOCK` to pin it, and Windows names a zone only in full, so there it's always an offset.

- What a note needs to say is what was replaced and why. When it happened is in the file's history and backups.

- The backup name was the other reader of the clock. 3.0 dated it so a second run didn't stop on the first run's copy and so one pattern found every backup. A count after `backup` does both, and the file's own mtime says when.

### Drivers in place of CLIs

- `style-guide_ui-ux.md` says the Go, Python, and C CLIs exist so the cross-binding check can compare them. Only Rust's is released.

- Each is about 3,000 lines. Their help text has to match byte for byte at 80 columns, a new write op means 8 dispatch sites, and `cli-regress.bash` runs all four.

- The check compares what the library does: stdout and the exit code for the same input and edits. A driver with 8 ops does that in a few hundred lines, and has no help text to keep in step.

- Each binding's corpus runner stays, and runs in its own test command.

### File tier

- Every binding keeps the full save, Windows extras included (JC, 2026-10-15). A file saved by a Go program and by a Rust one comes out the same, ACL and hidden flag included. Moving the extras to Rust and C only was weighed and turned down, since a program's save would then depend on its language.

- With the test CLIs gone, the Save outcomes cases run through each driver's `save` op, in all four bindings, on Linux and on the hosted Windows job.

- 4 of the Windows file defects in the backlog were in `migrate`'s old backup copy. v4 has one backup path, in `upgrade_file`.

### Merging keeps the receiver's text

- In 3.0 a merged document is written from its tree, so it's the one kind of document that loses its text. In v4 a merge is a list of edits like any other, and nothing about a document depends on how it was made.

- The common case for saving a merge is adding new defaults to a user's file. `user.underlay(defaults)` keeps the user's lines, adds what's missing with the defaults' comments, and saves like any edit.

- Which text a merge keeps is always its receiver's. The 2 directions exist so either document can be the receiver, and a fuzz property checks that they give the same values.

- The names put the argument's role in the verb. `merge_over` and `merge_under` were the first spelling and were turned down: `a.merge_over(b)` reads as "a goes over b" in English, and the call meant the opposite. An overlay goes on top and an underlay goes beneath, so `doc.overlay(x)` can only mean that `x` is on top.

- A merge comments out a receiver line it replaces rather than deleting it, as a setter does with a kept line. 3.0's merge dropped the base's extra repeated-leaf lines, so a merge then a save deleted typed text, against the README's first promise.

- The CLI's fold changes from left to right so FILE can be the receiver and keep its text. The two folds differ, as `design.md` says under Layered loading, so the change is written down here and pinned by a corpus case rather than left to turn up as a defect.

- Writing a merged document from its tree, as 3.0 does, was turned down. It would keep a second way to make text, and the comment rules that go with it.

### One file per binding

- One drop-in file matters for C, where the single header is the custom, and for Python, where vendoring a module is common.

- Rust and Go programs take a library through `cargo` and `go get`, and seldom copy a file in. One file there costs a 555 KB `lib.rs` and a 15,925-line `shcl.go`, which editors and reviewers both handle badly.

- `design.md` under Consumer API declined a whole-config decode because the reference can't have one in a single file with no dependencies. A `serde` feature would get around that: the derive macro is serde's, so shcl adds no macro crate of its own, and the feature would be off by default. It waits, under [Deferred](#deferred), since a serde decode is all or nothing. One field with a bad value fails the whole load, which is the TOML behavior the README argues against, and the doc's own lesson under [Format before ports](#format-before-ports) is to do less at once.

### Upgrade kept simple

- A format that changes needs a way forward for the files already out there, and SHCL's format will change again. So `upgrade` stays (JC, 2026-10-15).

- In 3.0 the 2.x support grew into 2 commands, 2 flags, a beta-stamp rule, a count of text that reads two ways, a backup helper, and 2 hints, and review rounds kept finding edges in it. 2026101419280001 was the last: a caller told to pass `from_v2` on every start could have a good file read by 2.x rules.

- v4 has one rule per question. The Format line says where a file came from, and only the caller can say otherwise. Each step converts what it's sure of. A line it isn't sure of stays as typed, where the load reports it, and the backup has the original.

- `upgrade_file` has no error type of its own. What can go wrong is a read or a write, and `IoError` already says which. 3.0's `UpgradeError` added `BackupTaken`, which the numbered backup name makes impossible.

- Since v4 keeps a file's lines, an upgrade is edits like any other. 3.0 made the file over the way `fmt` writes it, which lost its layout.

- A file with no Format line is taken as current. A file typed by hand follows the docs, and the docs describe this format. A program whose own old files have no Format line passes `from`.

### Format before ports

- 1.0.0 was tagged 17 days after the first commit. Since then comma lists became brackets, backslash escapes became `◉`, selectors went from brackets to parens, and `*` items became `- ` items. Bare spaces were banned and then allowed again. Each change was made 4 times, plus 4 CLIs, plus `migrate`.

- The Lexical edges table is the best part of `design.md`, and it came last. v4 builds the storage in Rust first, has Rust consumers use it, and only then ports it.

- The library version and the format version are separate. v4 is a library major on Format 3.

### Docs

- `design.md` tells most decisions as their history: what it used to do, when it changed, and what superseded it. That's a good record and a hard read. In v4 it says what the design is, in the present tense, and the history goes in a numbered decision log.

- 5 tables in `design.md` ended up as the fix for a rule applied at one site and not its sibling: Lexical edges, Load outcomes, Save outcomes, Write outcomes, and Kept lines under edits. v4 writes the tables first and makes a corpus case from each row.

- Text v4 makes wrong, to change when it's cut:
	- README.md's first bullet, "the save refuses rather than dropping it". A v4 save can't drop a line, so there's nothing to refuse.
	- README.md's second bullet, "attached to what they documented". A comment stays where it was typed.
	- `spec.md` under Canonical formatter, where `Max-Upload-MB:` comes back as `max-upload-mb:`, and the paragraph in `project/examples.md` that says the same.
	- `spec.md` under File tier and Layered loading, for the one save, the two merge calls, and the fold.
	- `comparison.md`'s memory numbers, run again.

## What stays

- Types chosen at read time, and the required fallback on `_or` reads.

- `Empty` apart from `NotFound`.

- A backslash as plain text, fenced raw blocks, and the rest of [value-syntax.md](value-syntax.md).

- The instance model, `(name, value, children)` merged on `(name, value)`. It's what sets SHCL apart from the formats it gets compared with.

- The schema as a flat list of `field:` entries.

- Stable diagnostic codes, and one bad line costing that line.

- One tokenizer per binding, and parity over idiom.

- Loose, Standard, and Strict.

- The corpus, the cross-binding check, and the fuzz properties.

- No user config file.

- `upgrade`, simpler.

## Alternative ideas

### Unconsidered

- An editor plugin or a language server.

- A streaming parse for files too big to keep in memory.

### Deferred

Each of these fits v4 and waits for after v4.0, so the first cut has less in it.

- A `serde` feature for Rust: `shcl::from_str::<T>(text)` and `shcl::from_document::<T>(&doc)`, a `Deserializer` over a document, off by default. Each field would be read with the typed read for its type, `Option<T>` would be `None` for `NotFound` and `Empty`, a `Vec` of a struct would read the field's instances, and a map a node's children. It's an all-or-nothing load, so it needs its own words in the docs about what it gives up, and that's its own item.

- Reading again only the blocks an edit touched, with the whole-document re-read as the thing to beat. The edit loop under [Node handles](#node-handles) costs edits times size with a whole re-read, which matters past about 1,000 instances in a 1,000-line file. Measure first.

- `Lookup.source` as a borrow of its line in Rust. One allocation per read, and a lifetime on `Lookup` to pay for it.

### Rejected

- One core, with the other languages calling it. Go would need cgo, which ends its plain cross-compile, and Python would need a compiled extension, which ends the one-file drop-in.

- A WebAssembly core, run inside each language. Every binding would need a runtime, which is a dependency.

- Dropping Go or Python. A native drop-in for each is part of what the README offers.

- Case-sensitive names. Matching without regard to case is friendlier to type, and only the output was the problem.

- Making a reopened block an error, as TOML does with a table defined twice. Dotted paths from anywhere are in the README's first example.

- Dropping Loose (JC, 2026-10-15). Its issues are settled.

- Dropping `upgrade` with the 2.x support. The next format change needs it (JC, 2026-10-15).

- Working out a file's format from its content. A typo in a current file can look like an old spelling, which is how 2026101419280001 came about.

- A generic read in Go. See [Reads](#reads).

- `--set` reading syntax and `--set-string` taking data, and `set_syntax` as the name. See [Source in a setter](#source-in-a-setter).

- A syntax tree with a node per token. See [Source text first](#source-text-first).

- Moving the Windows save extras to Rust and C only. See [File tier](#file-tier).

- A stale handle that fails on use, or a `Stale` status. See [Node handles](#node-handles).

- Handles that read but don't edit, an `_at(id, ...)` twin of every Rust setter, and `Lookup` as the answer to `node` and `remove`. See [Node handles](#node-handles).

- `merge_over` and `merge_under` as the merge names, and a merge that deletes a replaced line. See [Merging keeps the receiver's text](#merging-keeps-the-receivers-text).

- A merged document written from its tree. See [Merging keeps the receiver's text](#merging-keeps-the-receivers-text).

- An option for `fmt` that folds reopened blocks, and a `canonicalize()` that collapses blank lines. See [Canonical form moves no line](#canonical-form-moves-no-line).

- A dated backup name, and an `UpgradeError` beside `IoError`. See [Notes without a clock](#notes-without-a-clock) and [Upgrade kept simple](#upgrade-kept-simple).

- `parse_and_validate` as the one combined load left. `validate` is one call, so a load plus it needs no name of its own.

- Reading again only the touched blocks in v4.0. See [Deferred](#deferred).

- Other projects that keep a file's text through edits:
	- toml_edit keeps a TOML document's formatting. It's separate from the `toml` crate, which reads a document into types.
	- kdl-rs keeps a KDL document's formatting, and has `autoformat` beside it.

	- VS Code's jsonc-parser works out the smallest text edit for a change to `settings.json`.

- serde's `Deserializer` is a trait a library can implement with no macro of its own. The derive macro is in serde's own crate.

## Roadmap

1. Cut `v3.0.0-beta1` as 3.0 stands, with nothing from this doc. There's no 3.0.0 full release (JC, 2026-10-15).

2. Build v4 in Rust.
	- The renames, and the middle read tier out of Rust, Go, Python, and C++.
	- Names in canonical output as first typed, no units from field names, and no clock in notes or backup names.
	- The stored lines, the edits, `canonicalize()`, comment runs, and merging as edits.
	- `Options`, the load and save calls, and the generic reads.
	- Node handles, `NodeId`, `NodeMut`, and the node forms of the setters.
	- The crate split.
	- The Rust driver with the Save outcomes cases, and `crosscheck.bash` run against it.
	- `spec.md`, `design.md`, the corpus, and the corpus cases the fold change and the [Properties](#properties) call for.
	- The gate: the 3.0 corpus reads the same, as under [Properties](#properties).

3. Move the Rust consumers to it and run them for a while.

4. Port to C, then Go and Python, each with its driver. Remove the Go, Python, and C CLIs once all 4 drivers pass.

5. Fold `migrate` into `upgrade`, as under [Upgrade](#upgrade), with the 2 to 3 step cut down to the conversions it's sure of.

6. Cut v4.
